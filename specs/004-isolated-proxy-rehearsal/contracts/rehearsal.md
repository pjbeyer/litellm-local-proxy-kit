# Interface contract: isolated rehearsal

## Invocation

Proposed CLI: `make rehearse REHEARSAL_MANIFEST=/path/to/reviewed-rehearsal.json REHEARSAL_SHA256=<reviewed-sha256>`. The second value pins the exact manifest bytes independently of the manifest, binding all execution-affecting selections. The host copies reviewed files only from a configured rehearsal input root and verifies those same bytes before admission. Refuse symlinks, multiply linked files, path escapes, changing files and any unaudited filesystem source. Only that one Make target may be requested. `POLICY`, restart identifiers, inherited credentials, and arbitrary argv do not select rehearsal behavior. No fallback when a required input is absent. Output is one bounded JSON result on stdout; brief sanitized diagnostics may go to stderr. Exit `0` only for `passed`, `78` for refused input or missing isolation, `1` for failed checks, and `2` for unproved closure. Interrupted execution and missing terminal evidence are not passes.

The version-1 manifest has `version`, `overlay`, `pin`, `runtime_bundle`, `guest_image`, `fixture_set` and optional `native_receipt` and `fixture_trace`. File/bundle entries provide an explicit absolute path and expected lowercase 64-hex SHA-256; a runtime bundle is identified by its canonical packaged bytes, with the existing proof checking prepared guest files independently. `guest_image` is a provisioned immutable image identity with a verified digest; the adapter resolves it under a dedicated operator-owned image root, never relative to the proposal or installed controller. Reject unknown fields, duplicate keys, drift, runtime receipt omissions, unsupported fixture features, ambiguous inputs and executable settings. The guest only sees the verified, immutable input bytes. The image is not fetched as a side effect.

## Backend boundary

The single backend attests an owned scope with no network devices, no shared host files, no clipboard or credential bridge, no generic guest-to-host command bridge, and no host endpoint forwarding. Allow a read-only reviewed input volume, disposable work storage and a bounded one-way guest report channel. Admit only run-owned guest loopback services. Trusted guest admission probes and host device inspection must both pass; make no claim that an unrestricted user shell is contained. Connection, write, and credential denial cases use only disposable sentinels. Teardown identifies only the owned run and preserves the boundary through uncertainty.

## Admission and identity continuity

1. Reserve a durable, exclusive run ID before allocation. Create each object under that backend-owned namespace; the supervisor must be able to enumerate and reconcile owned objects by run ID even if allocation returns no handle. If it cannot, the backend fails qualification. Publish terminal closure evidence before releasing exclusivity. Worker failure with proved closure settles `failed`; absent or uncertain closure remains `incomplete` and blocks another allocation.
2. Verify host VM device policy before boot. Boot a trusted, independently reviewed guest supervisor with input volume read-only and inaccessible to the worker until admission. A privileged supervisor loads a reviewed guest policy to deny loopback by default except fixed per-run TCP probe and fixture endpoints; the candidate and helpers use an unprivileged account without supervisor devices, inherited descriptors or access to privileged control sockets. The v1 feasibility task must prove this design on the actual backend; a firewall declaration or missing host NIC alone cannot admit candidate execution. Before releasing the inputs, trusted inert checks under the same worker restrictions must observe the intended allowed and denied endpoints, including a distinct unapproved guest-local service.
3. Bind the runtime bundle digest to a closed inventory mapping guest paths, interpreter, import metadata, dependencies and applicable native receipt to exact bytes. Verify the prepared guest inventory before candidate import, keep it immutable for the run, then apply the existing provenance and sentinel checks. Confirm the listener derives from that launch and rerun proof before accepting success. Refuse a good bundle paired with different prepared guest files.
4. Permit only the trusted guest supervisor to send the result, excluding candidate descriptor inheritance and device access. The host compares the frame to the admitted VM scope, run ID, proposal/overlay/pin and runtime inventory identities, selected fixture-set digest and fully resolved fixture settings, then checks the whole declared required check set. A schema-valid result is not sufficient.
5. The only optional version-1 fixture setting is Boolean `fixture_trace`, default `false`; map it in the trusted guest to a fixed non-secret environment flag consumed by the local fixture adapter to select in-memory event counters. No arbitrary environment names/values or additional I/O. Include the actual resolved Boolean and fixture version/content digest in the canonical effective manifest. The environment-only acceptance pair changes this value; it does not change the overlay or runtime.

## Result

Versioned closed JSON. Include only the fields in the [data model](../data-model.md) and fully check them before rendering user-facing output. At most one final record with the expected run ID; absent, malformed, oversize or repeated records cannot pass. Host proof and guest results are distinct; host attestation is not guest-provided. No paths, raw inputs or response bodies, test key, opaque guest errors, or passthrough strings. Effective launch digest binds the exact sanitized fixture YAML and behavior-affecting setting values allowed by the schema; reject unknown behaviors rather than silently hashing or printing secrets. Keep timing, probe latency, and variable identifiers out of identity hashes unless needed by the identity contract.
