# Interface contract: isolated rehearsal

## Invocation

The [configuration check](configuration-check.md) is the routine path. This contract governs only the explicitly requested native path.

Proposed `make rehearse REHEARSAL_ROOT="$review_root" REHEARSAL_IMAGE_ROOT="$image_root" REHEARSAL_MANIFEST="$review_root/reviewed-native.json" REHEARSAL_SHA256="$reviewed_digest"`. All four arguments are required inputs to a trusted standalone Make invocation. Both roots and the manifest path must be absolute. The roots are separate, dedicated operator-owned directories for reviewed inputs and provisioned images; neither is inferred from the working directory, environment, installed state or manifest. The expected digest is supplied independently of the manifest. Apply root containment to the manifest and all entries, using the image root only for the provisioned image. Retain immutable copies of the verified bytes. Refuse symlinks, multiply linked or non-regular files, path escapes, changed bytes and any unaudited source. No `POLICY`, restart identifiers, inherited credentials, arbitrary argv or implicit fallback. Request exactly one Make target; mixed goals follow the [shared Make usage error rule](configuration-check.md#invocation-and-admission), not the receipt contract. With otherwise valid inputs and no qualified backend/image, refuse before candidate execution without a check result. Emit one bounded JSON result for each controlled disposition. If durable reservation or settlement remains indeterminate or interruption prevents a valid result, exit nonzero without claiming a disposition. The underlying CLI exits 0 for `passed`, 78 for refusal, 1 for failure, and 2 for `incomplete` (unproved closure or known uncommitted settlement). GNU Make normally reports 2 on any recipe failure; use the receipt for disposition. Interrupted execution without valid terminal evidence does not pass.

### Native reviewed-input rules

Assign the manifest, overlay, pin, runtime bundle, fixture set and optional receipt only to `REHEARSAL_ROOT`; resolve `guest_image` only from the trusted image inventory beneath `REHEARSAL_IMAGE_ROOT`. These path rules apply only to the native lane. Canonicalize each explicit root using the trusted host; refuse roots that overlap one another or any protected installed deployment, controller or credential-store location (overlap in either direction). Use the canonical root or the exact operator-supplied spelling of that root; an alias in an ancestor does not authorize other spellings. Reject symlinks below the root. Both native roots and every selected input must be on trusted mounted local storage verified before reading content; explicitly selected attached drives are eligible if the backend proves the same storage and lifetime controls. Refuse unknown, network-backed or automatically mounted storage without activating it.

Anchor path resolution to the same validated root object, not a later lookup by name. Admit mount identities before traversal and bind that decision to the validated root and each opened object before reading. Check containment, regular-file type, link count, size and digest on the opened object; refuse if it cannot be tied to that root. A provisioned image must remain bound to the verified read-only image object through use, not be reopened by an unchecked path. The backend must prove it consumes that object and its backing bytes remain immutable from verification through detach. A read-only handle alone is not immutability proof. For all other inputs, including the manifest, consume only retained immutable verified bytes. Replacing both a manifest and the digests inside it does not change the independently supplied expected manifest digest.

The version-1 manifest has `version`, `overlay`, `pin`, `runtime_bundle`, `guest_image`, `fixture_set` and optional `native_receipt` and `fixture_trace`. File/bundle entries provide an explicit absolute path and expected lowercase 64-hex SHA-256; a runtime bundle is a verified regular-file package that carries a closed inventory of the prepared guest files. The package digest and prepared inventory digest are distinct. `guest_image` is a provisioned immutable image identity with a verified digest; the adapter resolves it under a dedicated operator-owned image root, never relative to the proposal or installed controller. Reject unknown fields, duplicate keys, drift, runtime receipt omissions, unsupported fixture features, ambiguous inputs and executable settings. The guest only sees the verified, immutable input bytes. The image is not fetched as a side effect. Before qualifying an image/backend pair, publish and enforce positive byte ceilings for aggregate pre-reservation memory, total host staging, expanded runtime inventory, disposable guest storage and aggregate durable ledger storage (including transaction overhead). Keep unresolved records; reclaim only durably settled records under a published retention policy, outside new-run admission. Before reservation, prove that the ledger can durably accommodate both the reservation and its eventual settlement without exceeding its ceiling; otherwise return `refused` with `ledger_capacity_unavailable` and allocate nothing. The manifest is limited to 16 KiB. Enforce memory ceilings before and throughout reads, including retained inputs and verification buffers; stream the image digest from the held read-only object using bounded memory. Missing limits or a pre-reservation overrun yield a typed native refusal before allocation. Exceeding a limit is a typed non-success, with closure still required after reservation. Before reservation, the host may verify and retain inputs in memory and hold the verified read-only image open. No guest, on-disk staging, scratch, mount or backend run object may exist before durable reservation. After reservation and before guest admission, trusted host work is limited to verified opaque staging and backend setup, with every allocation bound to the run at creation. It does not interpret overlay, runtime bundle, pin or fixture content, execute candidate code or invoke candidate-bearing helpers.

## Backend boundary

The single backend attests an owned scope with no network devices, no shared host files, no clipboard or credential bridge, no generic guest-to-host command bridge, and no host endpoint forwarding. Allow a read-only reviewed input volume, disposable work storage and a bounded one-way guest report channel. Admit only run-owned guest loopback services. Trusted guest admission probes and host device inspection must both pass; make no claim that an unrestricted user shell is contained. Connection, write, and credential denial checks use only disposable sentinels. Establish that the selected host and guest prevent persistence of test-key-bearing memory via paging, saved state, snapshots and crash capture. Verify the control with inert marker data during qualification and release checks. If the backend cannot establish it, do not qualify it. For each run, before generating or using a test key, verify trusted current evidence that the host, guest image and backend configuration match the qualified protections and that those protections are active. Missing or mismatched evidence prevents key generation and candidate startup; after reservation the host follows the [closure and settlement rules](../data-model.md). Keep the protections enforced until key-bearing memory is discarded, including during isolation-owner loss and teardown. If the host cannot prove discard under those protections, closure is unproved. Teardown identifies only the owned run and preserves the boundary through uncertainty.

## Admission and identity continuity

1. Reserve a durable, exclusive run ID before allocation. Reservation takes effect at the atomic durable ledger commit, not its acknowledgement. When that outcome is uncertain, allocate nothing and keep the allocation fence until the trusted recovery authority inspects the durable ledger. Return `refused` only on proof that no reservation committed; if reservation is confirmed use normal closure rules. Without either proof, exit nonzero without claiming a terminal result. Create each object under that backend-owned namespace; the supervisor must be able to enumerate and reconcile owned objects by run ID even if allocation returns no handle. If it cannot, the backend fails qualification. Publish terminal closure evidence before releasing exclusivity. Enforce an independent backend compute cutoff no later than the verification deadline plus the teardown budget, even if the owner fails. Cutoff does not prove closure; keep the boundary and unresolved record until closure is proved. After reservation use the data-model receipt rules: `failed` requires durably settled closure; a known unsettled scope remains fenced, and an indeterminate settlement permits no terminal receipt.
2. Verify host VM device policy before boot. Boot a trusted, independently reviewed guest supervisor with input volume read-only and inaccessible to the worker until admission. A privileged supervisor loads a reviewed guest policy to deny loopback by default except fixed per-run TCP probe and fixture endpoints; the candidate and helpers use an unprivileged account without supervisor devices, inherited descriptors or access to privileged control sockets. The v1 feasibility task must prove this design on the actual backend; a firewall declaration or missing host NIC alone cannot admit candidate execution. Before releasing the inputs, trusted inert checks under the same worker restrictions must observe the intended allowed and denied endpoints, including a distinct unapproved guest-local service.
3. Bind the runtime bundle digest to a closed inventory mapping guest paths, interpreter, import metadata, dependencies and applicable native receipt to exact bytes. Verify the prepared guest inventory before candidate import, keep it immutable for the run, then apply the existing provenance and sentinel checks. Confirm the listener derives from that launch and rerun proof before accepting success. For native pins, before launch derive the expected loaded artifact path and digest from the verified pin, native receipt and sealed inventory; these must agree. Require trusted process-bound evidence of the actual loaded object, compare it with those expectations and revalidate continuity before success. Missing, ambiguous or mismatched evidence prevents a pass. A valid bundle paired with different prepared files must not start the proxy. After reservation the host follows the [closure and settlement rules](../data-model.md).
4. Permit only the trusted guest supervisor to send the result, excluding candidate descriptor inheritance and device access. The host compares the run ID and report channel with its reserved scope; it compares each `reviewed_inputs` digest, the resolved `fixture_trace` Boolean and required route/check set with its own admission record and versioned trusted fixture catalog. The host does not interpret fixture or proposal bytes or derive guest-only identities. The trusted guest supervisor derives `native_artifact_required` from the verified pin and validates native receipt and loaded-artifact evidence when required. The host checks coverage and receipt-presence consistency against that closed attestation. Prepared inventory, proposal and effective launch identity come from the trusted guest supervisor’s sealed expectations and revalidation; absent or uncertain continuity is non-success.
5. The only optional version-1 fixture setting is Boolean `fixture_trace`, default `false`; map it in the trusted guest to a fixed non-secret environment flag consumed by the local fixture adapter to select in-memory event counters. No arbitrary environment names/values or additional I/O. Include the actual resolved Boolean and fixture version/content digest in the canonical effective manifest. For each run the trusted supervisor observes the counter for the exercised stub completion route: it must advance once when tracing is enabled and remain unchanged when disabled. Report only the fixed check outcome; missing or inconsistent observations cannot pass. The environment-only acceptance pair changes the resolved Boolean, not the overlay or runtime.

## Version-1 proposal-to-fixture mapping

Inside the admitted guest, validate the reviewed overlay against the [closed v1 overlay subset](configuration-check.md#supported-overlay-fields-v1) and render the exact proposal. Derive the fixture configuration with the closed mapping below. The fixture catalog belongs to the trusted supervisor, not the requested fixture data. It fixes the stub route and model, local endpoint role, and test-authentication references. Only run-owned listener and stub addresses may be assigned at runtime; neither comes from the proposal.

| Rendered proposal setting | Required fixture disposition |
| --- | --- |
| `model_list`: declared model selectors, URL and upstream credential reference | Replace the entire list with the single catalog stub route and its run-owned loopback provider. Record `local_stub_provider`; exclude `provider_routes` and `real_credentials`. Never copy or resolve proposal credentials or contact the proposal URL. |
| `model_list`: `timeout` and `stream_timeout` | Do not carry over production timeouts. Use fixed catalog settings and the rehearsal deadlines; exclude them under `production_features`. |
| `general_settings.master_key` | Replace with the catalog test-key environment reference. Record `test_key_substitution`; the proposal reference is not carried over. |
| `litellm_settings` and `router_settings.fallbacks` | Omit these production settings. Use only catalog defaults and exclude them under `production_features`. |

No proposal value carries through unchanged by policy. Refuse any unsupported overlay field, unexpected rendered field or unfixed fixture setting; if discovered after reservation, stop before proxy startup and settle under the [host receipt rules](../data-model.md). The trusted guest supervisor checks that every rendered setting has a disposition, that the exact sealed YAML matches the catalog-derived configuration, and that the required substitutions and exclusions match the mapping before launch. The check does not treat matching digests alone as evidence of correct mapping. `fixture_trace` changes only the supervised fixture environment, not this YAML.

## Result

Versioned closed JSON. Include only the fields in the [data model](../data-model.md) and fully check them before rendering user-facing output. Limit the guest frame and public JSON receipt to 8 KiB each, including framing or newline. Apply the frame limit during receipt, before parsing. Accept exactly one complete frame with the expected run ID and trusted, run-bound end-of-report evidence (such as EOF on a supervisor-only bounded transport) before the verification deadline. Absent, malformed, oversize or repeated frames, trailing bytes or missing finality cannot pass. Host proof and guest results are distinct; host attestation is not guest-provided. No paths, raw inputs or response bodies, test key, opaque guest errors, or passthrough strings. The trusted guest supervisor establishes and retains the expected prepared inventory, rendered proposal and effective launch identities before candidate import or launch, as applicable, and checks the owned runtime and launch against them before reporting success. A candidate self-report or a comparison between two result fields is not revalidation. The effective launch digest binds the prepared runtime inventory, exact rendered proposal, exact sanitized fixture YAML, fixture content identity and resolved settings. The listener consumes the sealed fixture YAML verbatim. It contains only a fixed environment-variable reference for test authentication; inject the per-run key separately in memory. The supervisor verifies that no alternate configuration source is used and that the owned process uses the sealed launch inputs and observes and revalidates the loaded artifact’s identity for a pin declaring the optional native artifact, without claiming Rust-native route coverage. Reject unknown behavior rather than silently hashing or printing secrets. Keep timing, probe latency and run IDs out of identity hashes. The independently authorized same-host acceptance harness selects observation before launch outside the proposal and binds its private observer session to the confirmed reserved run ID. The trusted containment owner delivers the bounded opening event to the ready read-only observer over the host-only acceptance interface so it can take its declared sample; no observer request reaches the guest. For each same-host acceptance run, the trusted containment owner must give the external read-only observer fixed, sanitized, run-bound before/after liveness observations bracketing its during sample; an unverifiable bracket makes coexistence acceptance inconclusive. Use the host monotonic clock for both liveness observations and the independent sample’s start and end. On same-host acceptance only, the trusted guest supervisor can send bounded start/end liveness events on a separate supervisor-only one-way channel with the same access controls as the final report channel. The supervisor makes two live checks on a predefined schedule without observer commands. The qualified backend maps both check observations to conservative bounds on the host monotonic clock. Receipt time alone cannot substitute for an observation time when delivery can be delayed. The entire managed sample must start after the latest possible opening observation and end before the earliest possible closing observation. An unknown bound or a bracket that could exceed five seconds is inconclusive. Require the final supervisor report to attest that both events and the verified probes refer to the same candidate listener bound to the same run ID; the host verifies the event ordering and gives only sanitized acceptance evidence to the observer. T002 must prove the mechanism before it is used for acceptance. Require the same guest listener at both observations, no more than five seconds between them, and the complete managed sample strictly inside that interval. This is sampled coexistence, not continuous liveness proof. Keep this acceptance evidence separate from the final receipt. No candidate forwarding or new guest command channel.
