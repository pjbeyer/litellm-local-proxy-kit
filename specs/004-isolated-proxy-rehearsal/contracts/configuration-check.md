# Contract: routine configuration check

## Invocation and admission

Proposed standalone interface: `rehearsal-check --bundle-sha256 "$reviewed_digest"`. Proposed Make interface: `make -s -j1 rehearse-check REHEARSAL_BUNDLE_SHA256="$reviewed_digest"`. In either case the trusted caller pipes one complete bundle into stdin and closes the write end. Use the same trusted bootstrap at both boundaries. The Make target forwards the digest literally and passes the stream to the checker without reading, transforming or reopening it. This interface assumes a trusted checkout, Make invocation and toolchain on trusted local storage; arbitrary Make flags, overrides or inherited Make control variables are not supported. Reject an omitted or malformed expected digest, repeated standalone digest flags and obsolete routine path arguments. The trusted Make caller supplies exactly one assignment to `REHEARSAL_BUNDLE_SHA256`; GNU Make resolves its own assignments before dispatch, and the checker validates the single value it receives. If either rehearsal target is combined with any other goal, Make stops before any recipe, exits nonzero and emits a fixed usage diagnostic on stderr with no JSON on stdout.

The operator supplies only credential-free reviewed proposal data and approves the exact final bundle bytes alongside the exact decoded members. Record the expected bundle SHA-256 in a separate trusted review record before the check. Do not derive the expectation from stdin, an adjacent untrusted file or a fresh hash of the stream about to be checked. Packaging, source selection and the stdin producer are outside the check: the operator must not feed managed files, credentials or unreviewed data. The checker attests byte identity, not filesystem provenance or the behavior of the supplying process. Accept stdin only as a caller-opened pipe descriptor (reject regular files, sockets, terminals and other descriptor types); the supported invocation uses an anonymous local pipe. Neither entry point may open proposal paths, run a producer, resolve references, or fall back to files, environment data or native rehearsal.

### Bundle and manifest wire format (v1)

1. Read one stream to EOF, with a **768 KiB** cap on raw bytes enforced during the read, before decoding. Do not accept a valid prefix without EOF. A read failure, unsupported descriptor, empty input or cap overrun is `refused/input_invalid`; the whole-operation deadline applies while awaiting bytes or EOF. Compute SHA-256 over all bytes, including any trailing JSON whitespace, and compare with the independently supplied lowercase 64-hex digest before parsing any bundle content. A mismatch is `refused/digest_mismatch`.
2. Decode one UTF-8 JSON object with no BOM and no trailing non-whitespace data. Its exact required keys are `manifest`, `overlay` and `pin`, with optional `baseline_overlay`. Every value is a string in canonical RFC 4648 standard Base64: required padding when applicable, no embedded whitespace, and re-encoding the decoded bytes must reproduce the string. Do not extract archives, decompress or materialize members on disk. Enforce the role-specific byte limits during decoding or by preflighting encoded lengths and checking decoded lengths immediately; reject nested envelope values and duplicate keys. The envelope has no path, file type, compression or executable metadata.
3. Parse the retained manifest bytes as one UTF-8 JSON object with no BOM and no trailing non-whitespace data. Exact keys: integer `version: 1`, string `mode: "configuration_check"`, `overlay`, `pin` and optional `baseline_overlay`; each role entry is exactly `{sha256}` with a lowercase 64-hex digest over the exact decoded member bytes. Reject duplicate/unknown keys, wrong types or versions, native manifests and any missing or extra member, including disagreement about baseline presence. In both JSON objects, reject nesting beyond the declared shape and non-finite numbers; bound parser work even for a digest-matching malformed input. Hash the retained member bytes against the manifest before parsing any overlay or pin. A malformed envelope, manifest or member encoding is `refused/input_invalid`; a decoded member digest mismatch is `refused/digest_mismatch`.
4. Parse and render only the retained, verified bytes. Never interpret a member as a path or reopen it. The admission order above applies after any startup prerequisite has been met; no unverified render interpreter, parser dependency or renderer may run to inspect the bundle.

## Offline work and bounds

Run only the trusted checkout's parser, `core/render_config.py` render function and `core/config.template.header.txt` with already-installed trusted dependencies. Parse the admitted pin bytes as UTF-8 TOML, requiring a nonempty string `base_version` and a `patch_tip` of 7–40 lowercase hexadecimal characters. Treat all other pin metadata as opaque: do not resolve paths, sources, references or receipts. Do not call runtime provenance or sentinel entry points. Pass a fixed synthetic `HOME` (`/rehearsal-home`) explicitly; inherit no behavior-affecting environment or credentials. Render both overlays with the same trusted renderer, template and context. Derive `render_context_sha256` from a closed object `{version, renderer_sha256, template_sha256, parser_inventory_sha256, python, pyyaml, settings}` with `version: 1`. Hash the exact trusted `core/render_config.py` and tracked header bytes into their named fields; both renders must execute code derived from those exact renderer bytes and consume those exact header bytes. Use `{implementation, version, executable_sha256, inventory_sha256}` for `python` and `{version, inventory_sha256}` for `pyyaml`. Hash inventories as closed maps of component-relative names to exact-byte digests (no host paths). The parser inventory covers the exact reviewed checkout code used to parse and normalize admitted data, including comparison inputs; standard-library and package parser components remain covered by their respective inventories. The Python inventory covers the trusted interpreter distribution’s standard library and native runtime dependencies used during startup and rendering; the PyYAML inventory covers the trusted package’s importable files and native extensions. Use a trusted bootstrap and a stable trusted installation with no ambient import sources. Both entry points use the same read-only trust record supplied by the trusted local kit/toolchain installation, independently of the input stream. The record binds renderer, header and parser inventory digests from the reviewed checkout revision and interpreter and dependency digests from trusted installation records established before the check. Never promote observations from the current invocation into expectations. If that reference is missing or mismatched, stop before renderer or dependency execution and return `failed` with `render_failed`. Before starting the render interpreter, the trusted bootstrap verifies its executable and startup dependencies against the trust record and establishes continuity of those verified objects into startup. If it cannot, both entry points emit bounded `render_failed` without starting that interpreter. Verify the expected renderer, parser and render dependencies before loading them, and bind both renders to the verified executable and exact render-affecting code used, including loaded native images. Do not use cached renderer or dependency bytecode unless its exact bytes are included in that identity. A mismatch detected at admission prevents rendering; lack of identity or continuity cannot yield `checked`. The fixed settings object is `{"HOME":"/rehearsal-home"}`. Use and identify the same trusted dependencies for both renders; an unidentified context is non-success. Hash the UTF-8 JSON object with sorted keys, ASCII escapes and no insignificant whitespace; do not include paths, ambient environment, or timestamps. The check is for reviewed data, not a sandbox or a compatibility check.

### Supported overlay fields (v1)

The proposal and any baseline use the same closed subset of the kit overlay. Required fields are marked below; other listed fields are optional. No coercion, nulls, unknown fields, or silently dropped settings.

| Field | Admitted value |
| --- | --- |
| `master_key_env` (required), `upstream.api_key_env` (required) | Environment variable name matching `[A-Z_][A-Z0-9_]*`; never resolved. |
| `upstream.api_base` (required) | Absolute HTTP(S) URL with a host and no userinfo, query, fragment, whitespace or substitution placeholders; held as data, never resolved or contacted. |
| `upstream.models` | Sequence of maps with required nonempty `name` and optional `timeout` and `stream_timeout` (positive integers in seconds). Model names must be unique. `*` is reserved for the wildcard flag. |
| `upstream.wildcard`, `upstream.wildcard_timeouts` | Booleans. `wildcard_timeouts` may be supplied only when `wildcard` is true. Require at least one named model or `wildcard: true`. |
| `litellm_settings` | Map with only Boolean `drop_params`, `modify_params` and `telemetry`, and positive integer `request_timeout` (seconds). |
| `router_fallbacks` | Sequence of maps with a unique `from` and a nonempty `to` sequence of distinct names; names must refer to declared named models. Preserve destination order. |

Names contain only ASCII letters, digits, `.`, `_`, `-` and `/`. Reject all other fields, including `extra_model_list`, `general_settings` overrides, `litellm_settings_addendum`, callbacks, and MCP servers. The renderer still generates `general_settings.master_key` as a reference. The check does not cover production-only settings: prepare a reviewed overlay in this subset or accept refusal; the check never strips unsupported fields on the operator's behalf.

Budget: decoded manifest 16 KiB, decoded pin 32 KiB, each decoded UTF-8 overlay 256 KiB; at most 4,096 parsed nodes and nesting depth 24 per overlay. Use a safe, bounded YAML subset: reject aliases/anchors, merge keys, duplicate or non-string map keys and explicit tags. Cap each in-memory render at 1 MiB and the complete CLI operation at 10 seconds, including input and EOF wait, all parsing, trusted startup and render-context verification, both renders, and result validation. On timeout return `failed/deadline` without partial output for controlled outcomes. No file creation or modification by the CLI or Make recipe, including temporary files, interpreter caches, rendered configuration or a run ledger. No downloads. Raw data, parser exceptions and host-local fields never reach stdout/stderr.

## Result and process status

The standalone CLI and Make both emit exactly one closed JSON object on stdout (maximum 4 KiB) for every controlled outcome of a dispatched single rehearsal-check target or standalone check CLI: `version: 1`, `mode: "configuration_check"`, `runtime_not_exercised: true`, `status` (`checked`, `refused`, `failed`). `checked` includes `bundle_sha256` (SHA-256 of the exact complete stdin stream), `manifest_sha256` (SHA-256 of the exact decoded manifest bytes), `overlay_sha256`, `pin_sha256`, `template_sha256`, `render_context_sha256`, `rendered_sha256`, and `categories_present`. It includes `comparison: null` when no baseline was supplied, otherwise a closed object with `baseline_overlay_sha256`, `baseline_rendered_sha256` and `changed_categories`. Category IDs in fixed order are `model_list`, `litellm_settings`, `general_settings`, and `router_settings`; any other rendered top-level key is a render failure. Compare their parsed values in memory (mapping order ignored, sequence order significant); list only changed categories, including additions and removals. Emit category IDs in fixed order and never include caller-defined keys, values, names, paths or raw diffs. An empty comparison list means no differences in those categories under this render context; `null` means no comparison. All admitted inputs are reviewed and secret-free; use only references, never resolved credentials.

For `refused` and `failed`, omit all success fields and include one fixed `reason`: `input_invalid` or `digest_mismatch` (refused), `render_failed`, `output_limit` or `deadline` (failed). Ordinary process interruption without a result is non-success. The underlying CLI returns 0, 78, or 1 respectively; GNU Make returns nonzero on recipe failure (normally 2), so Make consumers use the typed result for disposition. Check success requires both exit zero and a valid `checked` object. Make must not mix this target with any other target. Neither `checked` nor absence of output establishes runtime behavior, equality to production, or approval to stage or activate anything.
