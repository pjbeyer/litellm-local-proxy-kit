# Data model: isolated rehearsal

- **Native proposal**: Versioned operator-supplied manifest; explicit overlay and pin files and reviewed SHA-256 values; approved guest runtime bundle and image identifiers; optional native receipt required when the pin declares it; one named local fixture set. Host paths are invocation inputs, never receipt values. Manifest unknown fields refuse. No arbitrary shell hooks, environment map, destination URLs or launcher argv.
- **Run scope**: Non-reusable run ID; exclusive private record created before allocation; sealed runtime and input identities; run-owned hypervisor handle, scratch owned by that record, and supervised guest endpoint. The handle/local paths are private recovery state, not public results. Allocation is distinct from startup; admission precedes all candidate-bearing operations.
- **Guest result**: One bounded supervisor-only frame: version, run ID, `reviewed_inputs`, `runtime_inventory_sha256`, `proposal_sha256`, `fixture_yaml_sha256`, `effective_launch_sha256`, `build_id`, Boolean `native_artifact_required`, resolved Boolean `fixture_trace`, required check outcomes, and coverage declarations. `reviewed_inputs` is a closed map of exact admitted-byte SHA-256s for `manifest`, `overlay`, `pin`, `runtime_bundle`, `guest_image`, `fixture_set` and `native_receipt` (null if absent); the host has the independent expected values. The supervisor compares the prepared inventory with the reviewed bundle inventory before candidate import. Before launch it captures the proposal digest from exact rendered UTF-8 bytes and the effective digest from the canonical object `{runtime_inventory_sha256, proposal_sha256, fixture_yaml_sha256, fixture_set_sha256, fixture_trace}`. It revalidates these guest-owned identities against the sealed inputs and the owned process before it reports success. Structured digests use UTF-8 JSON with keys sorted, no insignificant whitespace, ASCII escapes and no non-finite numbers; sort inventory entries by guest-relative path. Paths may be used in the inventory digest, never transmitted as evidence. The test key and raw output are not digest inputs. For same-host acceptance only, require `same_listener_observed: true` in the supervisor frame for coexistence credit; omit this field outside same-host acceptance and never copy it into the public receipt. Retain it privately with the two run-bound observation records, their host-monotonic bounds and the independent managed sample. The host verifies the observations and correlation separately from the native receipt.
- **Comparable build ID**: `build_id` is `{version: 1, source_commit}`. `source_commit` is the full lowercase 40-hex Git commit from verified patched-source provenance, not the configured pin prefix. The guest supervisor binds it to the candidate listener through verified runtime and process continuity. An independent read-only observer obtains the same field from the managed listener’s verified runtime provenance and binds it to that live process. For SC-001 require different full commits; equal, unbound, missing or incomparable IDs cannot establish a different build. This intentionally does not claim to distinguish two builds of the same source revision.
- **Checks and coverage**: Required check IDs are `environment_admission`, `runtime_provenance`, `patch_sentinel`, `liveness`, `readiness`, `unauthenticated_rejection`, `test_key_acceptance`, `fixture_routes`, `fixture_trace_observed` and `identity_continuity`; each is `passed` or `failed`. `identity_continuity` passes only if the trusted supervisor verifies each accepted probe connection and response against trusted evidence binding it to the reserved run’s owned serving process and listener, and final revalidation agrees. Endpoint reachability, matching payloads and final-only observations are not attribution. Missing or ambiguous per-probe linkage cannot pass. Route records `{id, feature, result}` also use `passed` or `failed`. The v1 trusted catalog binds `health_liveness` and `health_readiness` to `health_endpoints`, `unauthenticated_rejection` and `test_key_acceptance` to `auth_checks`, and `stub_completion` to `local_stub_route`. A pass requires the exact check and route sets, with no duplicates, ambiguity, or failed entries. `exercised_features` equals the features of the route set; `substitutions` names fixture replacements and `exclusions` contains `{feature, reason}` omission records disjoint from exercised features. For this v1 catalog, a pass requires both `local_stub_provider` and `test_key_substitution` in `substitutions`, and the three base `exclusions` entries `provider_routes`, `real_credentials` and `production_features`, all with reason `not_in_scope`. The native-pin rule below defines the only additional exclusion. The trusted supervisor verifies the [closed proposal-to-fixture mapping](contracts/rehearsal.md#version-1-proposal-to-fixture-mapping) before launch. Unsupported selections visible in the host manifest refuse before reservation. If the guest finds unsupported fixture content after reservation, stop before candidate execution and settle by the host closure rules. Never silently drop unsupported features. The v1 route catalog does not claim Rust-native route coverage. For a pin declaring the optional native artifact, `runtime_provenance` verifies its bytes and receipt, and the trusted supervisor observes and revalidates the loaded artifact’s path and hash in the serving process as part of `identity_continuity`; never transmit the path or claim native feature coverage from loading alone. Record native feature coverage as an additional `native_features` exclusion with reason `not_in_scope` for those pins. Partial guest evidence on non-success cannot stand in for these pass requirements. Missing or unknown required evidence cannot be represented as a pass; omit unvalidated guest evidence from the host receipt.
- **Host receipt**: Closed record with version, run ID, status, guest evidence, failure class, host closure evidence, `started_at` and `finished_at`. `started_at` records reservation, not candidate startup, and is null before reservation; the other nullable fields follow the status rules below. Guest evidence is null unless the host validated the frame against the admitted scope. Sanitized evidence survives guest disposal. Proved closure is a host-only record tied to the run ID, with a fixed method (`no_allocation`, `supervisor_attest` or `backend_reconcile`). `no_allocation` requires affirmative evidence that no run resources were ever created. Otherwise the trusted host authority must account for termination or removal of the run-owned VM, processes and descendants, endpoints, mounts and scratch, with no surviving or unidentified objects under the reserved scope. Missing or contradictory observations never count as proved closure. A completed cleanup with settlement known not to have committed by the deadline remains unresolved: report `incomplete` when controlled output is possible, keep the cleanup proof private and retain the fence. The durable ledger is authoritative for allocations. If a settlement commit is indeterminate, exit nonzero without a terminal receipt; preserve the allocation fence. On recovery, read the original ledger and verify durable closure before clearing the fence. An already committed result is historical; recovery cannot supply the missing successful exit and receipt or upgrade the original invocation.
- **Configuration check**: Separate closed manifest and result defined in the [check contract](contracts/configuration-check.md). It has no run scope, runtime receipt, probe, timestamp or teardown field. A baseline comparison is optional and never observes live state.

**State machine**: `reserved → admitted → running → closing → settled`. A failure after reservation may go directly to `closing`; closure must cover all resources, or attest that none were created. Write the settled result and closure proof before releasing exclusivity. A new invocation refuses unresolved records before reservation, without attempting another run. The trusted backend recovery authority reconciles on owner recovery or an explicitly authorized recovery action, never on a new rehearsal invocation. It may act only on the original owned scope and may settle it as `failed` only on durable evidence of closure; it never manufactures a `passed` result.

`failure_class` is closed: `refused` permits `input_invalid`, `digest_mismatch`, `backend_unavailable`, `unresolved_run`, `ledger_capacity_unavailable` or `deadline`; `failed` permits `admission_failed`, `runtime_failed`, `probe_failed`, `identity_failed`, `report_invalid`, `interrupted` or `deadline`; `incomplete` uses `closure_unproved` if closure is unproved, or `settlement_unconfirmed` if closure is proved but settlement is known not to have committed by the deadline. Both replace the initiating failure. `passed` uses null.

| Status (CLI exit) | Required evidence |
| --- | --- |
| `refused` (78) | Before reservation, with null run ID, guest, closure and `started_at`; include a fixed refusal class and `finished_at`. |
| `failed` (1) | After reservation, with run ID, fixed failure class, durably settled host-proved closure, and both timestamps. If a validated guest frame had arrived, retain its sanitized evidence. |
| `incomplete` (2) | After reservation, with run ID, fixed failure class, `started_at`, and null `finished_at`; null public closure (unproved or not durably settled). If the outcome of a settlement commit is unknown, use the no-receipt rule above instead. Retain the unresolved scope. |
| `passed` (0) | Run ID, both timestamps, full validated guest evidence with required checks passed and identity revalidation, durable host-proved closure, and null failure class. |
