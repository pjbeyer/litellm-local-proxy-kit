# Feature Specification: Isolated LiteLLM rehearsal

- **Feature Branch**: `feat/isolated-proxy-rehearsal`
- **Created**: 2026-11-26
- **Status**: Pre-implementation specification; current-revision comprehension and execution authorization are separate gates

This contract owns isolated proposal rehearsal. [Spec 003](../003-restart-controller/spec.md) owns managed preparation, qualification, and restart; neither workflow may assume the authority of the other. This work does not change the repo-wide Spec Kit scaffold or the live controller reconciliation.

Rehearsal support has two tiers. The routine default is a **configuration check**: it verifies the reviewed inputs, renders the proposal with the kit's trusted renderer, and reports a summary and, if supplied, a reviewed-baseline comparison — with no guest, no candidate execution, and no contact with the managed proxy. The isolated native rehearsal below is an **explicit opt-in** that exercises the actual candidate runtime in a disposable offline guest; routine use never requires it and it is never selected automatically. An external drive or a separate macOS runner may host the opt-in lane, but the design must not require extra local hardware.

## User Scenarios & Testing

### User Story 1 — Test a proposal before staging it (Priority: P1)

The routine path is a **configuration check** (`make rehearse-check`): an operator chooses a reviewed deployment overlay and a runtime pin document. A build, native receipt, fixture or guest image is not needed for the check. The check verifies the reviewed input bytes, renders the proposal with the kit's trusted renderer, and summarizes the rendered configuration and reports changes only against an explicitly supplied reviewed baseline overlay — with no guest, no candidate code executed, and no contact with the managed proxy. Its result states explicitly that the configuration was checked but the runtime was not exercised.

The **explicit opt-in** is the isolated native rehearsal (`make rehearse`): the exact candidate is verified, starts on a loopback-only test endpoint inside a disposable offline guest, and passes the declared checks without real provider calls. It is requested by name; it is never selected automatically or as a fallback, and routine use never requires an external drive, a separate Mac, or any extra local hardware.

**Independent Test**: For the default path, render a reviewed overlay and pin pair and confirm the report identifies the fixed configuration categories changed against a reviewed baseline while no candidate process starts and no managed endpoint is contacted. For the opt-in lane, rehearse a pinned candidate build with a local fixture while another proxy is running; retain the result and independently observe coexistence and managed state as specified under SC-002.

1. **Given** a valid candidate and an available isolated runner, **when** the operator explicitly invokes `make rehearse`, **then** the exact candidate is verified, starts on a loopback-only test endpoint, and passes the declared checks without real provider calls.
2. **Given** unavailable isolation or a missing required input, **when** the isolated rehearsal is requested, **then** it returns a typed native non-success without executing candidate code or borrowing managed inputs or permissions, and it never downgrades to a configuration-check result. Before run reservation it refuses; after reservation, the result depends on closure proof and durable settlement. A mismatch discovered by isolated runtime verification prevents proxy startup.
3. **Given** a candidate that fails to start, exits, or loses identity during a probe, **when** rehearsal ends, **then** it reports a non-success outcome and cleanup only concerns resources owned by that rehearsal.
4. **Given** a valid reviewed overlay and pin, **when** the operator invokes `make rehearse-check`, **then** the exact reviewed inputs are verified, the proposal is rendered with the trusted renderer, and a bounded report summarizes the proposal and identifies changes when a reviewed baseline was supplied — with the candidate never executed, no guest, and no managed endpoint or credential contacted.
5. **Given** any missing, drifted, or ambiguous input for `make rehearse-check`, **when** the check runs, **then** it refuses with a typed error and produces no rendered output that could be mistaken for a validated deployment.

### User Story 2 — Know what the result does not prove (Priority: P2)

An operator can distinguish a passing isolated rehearsal from a configuration check, a production controller qualification, a successful `make prepare`, or permission to activate anything. A configuration-check result asserts only that the reviewed inputs were admitted and rendered under the check contract; it makes no claim that the candidate runtime starts, answers, or passes any probe, and the result cannot be presented as rehearsal evidence.

**Independent Test**: Compare the configuration-check result, the rehearsal result, and operator documentation with the existing controller contract. Confirm there is no approval record, restart plan, or automatic promotion path, and that the check result is labeled and schema-typed so it cannot substitute for an isolated rehearsal outcome.

## Requirements

- **FR-001**: Both lanes require an independently pinned, closed manifest and explicit reviewed input digests. Assign each input to its allowed root and verify and retain the same opened bytes through use. Never use `POLICY`, executable deployment settings, or managed inputs as fallback. The configuration manifest admits only the overlay, pin document and optional baseline overlay; native execution requires its separate reviewed manifest and qualified backend. No unattended execution or automatic switching between lanes. Reports identify admitted data by digest, not path.
- **FR-002**: Reuse the kit renderer, runtime provenance checks, and patch sentinel in proof-before-sentinel order within the isolated rehearsal. Verify the interpreter, source, pin and applicable native receipt inside the runner; bind the owned proxy process and its listener to the same verified versioned runtime and effective configuration held stable through probing. Recheck runtime proof and effective input identity before accepting success; verify the loaded native path and hash in the serving process for pins declaring the optional native artifact. Loading alone is not evidence of native route coverage. Reject drift or uncertain continuity. Do not rebuild, install over or edit a serving runtime.
- **FR-003**: For native rehearsal, establish an enforceable boundary before interpreting overlay, runtime bundle or fixture content, or invoking the candidate interpreter, renderer, provenance or sentinel helpers, fixtures, or startup; keep it in force through cleanup. Before containment, trusted host admission is limited to parsing the bounded closed manifest, checking explicit roots, and verifying and staging reviewed inputs as opaque bytes. Deny access to real credentials and credential stores and to managed listener, database and controller endpoints. No managed files may be writable. Deny network access by default except for explicitly admitted run-owned loopback connections needed for fixtures and probes; imported helpers and descendants inherit the same restrictions. Do not inherit host secrets, sockets or session environment. Use an ephemeral in-memory test key and disposable state. Verify the boundary with trusted negative probes before candidate-bearing work, or refuse. A clean environment and a loopback bind alone do not qualify. Real-provider checks are separate, explicitly authorized work, not a relaxation flag.
- **FR-004**: Attribute every accepted probe to the same owned proxy instance and endpoint. Check liveness, readiness, unauthenticated rejection and test-key acceptance. Stop verification on an occupied or ambiguous endpoint, identity loss or replacement. After reservation, report `failed` only with durably settled closure. Report `incomplete` when closure is unproved or settlement is known not to have committed and controlled output is possible. If settlement is indeterminate, exit nonzero without a terminal receipt and retain the allocation fence. Local fixture route checks are allowed; report exactly which routes and features were exercised.
- **FR-005**: Bound verification, startup, probing and teardown. Create a durable run record before executing candidate code. Clean up only resources created by the run on success, failure, SIGINT and SIGTERM. Assign cleanup to an isolation owner independent of the CLI and the candidate-bearing worker. Keep restrictions active until closure of all owned processes, descendants and endpoints is proved. If the isolation owner fails too, the boundary must persist or stop the entire owned scope; unproved closure cannot pass or release the allocation fence. Preserve a sanitized record and have the next invocation detect unresolved runs before new candidate work; do not repeat or widen cleanup.
- **FR-006**: A passing native receipt binds the host-admitted manifest and selected artifact digests to the guest-verified prepared runtime inventory, exact rendered proposal, effective launch identity and required checks. Distinguish a pre-reservation refusal from a reserved run with durably settled failure or unresolved closure or settlement. Return success only with the required checks, identity revalidation and independently proved, durably settled host teardown. Verify the closed proposal-to-fixture mapping before launch and declare substitutions and exclusions; unknown evidence required for a pass is non-success. Omit credentials, raw responses and host-specific paths. Never include the ephemeral key in the report or any digest input.
- **FR-007**: Never use launchd service control, call the live controller, change installed files, create approval/qualification records, or promote a proposal. Do not change `make prepare` or the startup supervision canary. Unsupported production features must be refused or explicitly marked unexercised, never silently omitted and claimed tested. The configuration check never elevates itself: its outputs are advisory and carry no authority to stage, prepare, restart, or qualify anything.

- **FR-008**: The routine check may read only explicitly reviewed data from a separate operator-owned staging root and trusted kit code, template and dependencies. Admit only the closed overlay subset in the [configuration-check contract](contracts/configuration-check.md); refuse unsupported settings rather than removing them. Parse the pin as metadata without runtime proof or candidate imports. Render offline with a fixed synthetic context. Emit a bounded, closed advisory result with `runtime_not_exercised: true`, binding the admitted manifest and trusted render context and using only fixed-vocabulary summaries; no raw YAML, arbitrary values, credential resolution, networking, managed state reads, or persistent run artifacts. Missing or invalid inputs and failed rendering are non-success; no partial success report.

## Security Considerations and Edge Cases

- A credential-free isolated runner is a prerequisite even for a candidate interpreter used only for verification or rendering. A trusted isolation supervisor may provision and observe its own run boundary and emit sanitized evidence; it does not invoke managed credential resolvers or use candidate inputs to control the host. The configuration check has no such prerequisite because it never executes candidate code; still, its renderer inputs are limited to the same reviewed, digest-verified bytes, and it must not render with `POLICY`, live deployment settings, or managed values as fallback.
- An occupied endpoint, replaced listener, changed runtime, or missing proof is not a successful test. Failed or uncertain cleanup is not a pass and must not tear down containment around surviving resources.
- An independent observer may read managed evidence solely for acceptance, outside the runner. It is not an input or credential source for the candidate.
- A configuration-check result that renders successfully is not evidence that the candidate build works. Any workflow, script, or operator step that treats a check result as rehearsal, qualification, or promotion evidence is a defect.

## Scope decisions and trade-offs

- Prefer a separate short-lived runner over extending the live controller RPC. `prepare` requires a managed primary and uses controller-bound assets and potentially shared dependencies.
- The existing wrapper needs a service-account token early in startup and can fall back to Keychain. Reuse its safe building blocks, not the normal resolver path; do not weaken the managed path or change its trust inventory without review.
- The routine default is the configuration check on this machine: it needs no guest, no VM image, no external drive, and no extra hardware, and it uses existing dependencies and bounded in-memory inputs and output, with no persistent run artifacts. The isolated native rehearsal is an explicit opt-in requiring the offline guest backend. An external drive or a separate macOS runner may host that opt-in lane, but neither is required for routine use and neither is selected automatically.
- The planned native backend is an offline macOS VM. Explicitly selected storage on an external drive does not change the same-host evidence rules. A separately qualified macOS runner can exercise native behavior, but cannot satisfy SC-002 for the managed proxy on this Mac. No transparent remote dispatch or alternative backend is part of the first implementation. A full second managed deployment, a profile system, provider calls, and controller or guard changes are out of scope.

## Acceptance Criteria

- **SC-001**: Select and verify a real patched build different from the running managed proxy, exercise it against local fixtures, and report the exact selected and effective identities. An independent read-only observer attributes build identity to the running managed listener; compare that observation with the verified candidate build identity using the common versioned build ID defined in the [data model](data-model.md). The verified full source commits must differ. A missing, incomparable or ambiguous identity makes the different-build claim inconclusive. Demonstrate that an allowed environment-only change changes both the effective identity and the observed fixture counter behavior and that omitted features are not credited; a stub-only startup does not pass this criterion.
- **SC-002**: An independent read-only observer outside the runner declares its managed asset and state inventory before the run. The managed listener must retain the same process identity before, during and after the run, and the entire during sample must fall within the run-bound liveness bracket defined in the [native contract](contracts/rehearsal.md#result). Compare before/after asset digests and controller policy, qualification, bootstrap and durable operation/recovery evidence for equality. These are point observations, not proof of continuous integrity. Incomplete or ambiguous observations, including concurrent owner changes obscuring attribution, are inconclusive and require a controlled rerun.
- **SC-003**: Exercise changed inputs after operator review; missing isolation before any candidate helper runs; denied managed paths, credentials and egress across candidate-bearing stages; missing or changed runtime and launch identity; occupied or replaced listeners; startup/probe errors; SIGINT, SIGTERM and worker loss; and failed teardown with containment still active. Use disposable sentinels rather than any live protected target for negative tests. Require non-success outcomes and no mutation of the protected sentinel or target. Demonstrate that a new invocation reports the unresolved run without starting another candidate. Also exercise the configuration-check negatives: missing or drifted digest inputs, an overlay that fails rendering, and a refusal path that emits no rendered output.
- **SC-004**: Existing Makefile maintenance tests remain green. A passing result — from either the configuration check or the isolated rehearsal — makes no claim about live inference, production credential compatibility, controller qualification, restart authorization, or unexercised behavior.
- **SC-005**: On a standard workstation with offline dependencies already available, check a reviewed overlay and pin without a VM, image, candidate bundle, external drive, or separate runner. Demonstrate identical results for identical reviewed inputs and trusted render context, a bounded delta with a reviewed baseline, and explicit no-comparison without one. Verify no candidate import/process, network or managed access, or file creation or modification, including temporary output and interpreter caches. All controlled results are bounded and typed with `runtime_not_exercised: true`; native implementation is not needed to verify this criterion.
- **SC-006**: Verify that the native receipt validator rejects a valid configuration-check result and that a valid native request with an unavailable backend returns a typed native refusal, not a check result, at both the CLI and Make boundaries. A release claiming both lanes needs their respective acceptance evidence, including this compatibility check.
