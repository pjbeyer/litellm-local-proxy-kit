# Feature Specification: Hermes Exact Quality-Eval Attribution

- **Created**: 2026-11-24
- **Status**: Draft for maintainer review. No transport is qualified; scoring stays off.
- **Audience**: LiteLLM Local Proxy Kit maintainers and evaluation operators.

A routed model name says where a request was sent, not whether its response became the answer Hermes saved. Add an opt-in Hermes plugin for `smart-router` and other explicitly configured LiteLLM aliases. Match the accepted response's proxy call ID and a plugin-issued token to one SpendLog, then link that exchange to the persisted user and final assistant message UIDs. Never match by timing, model name or session affinity.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Attribute the answer that was actually kept (Priority: P1)

As an evaluator, I can identify the exact user message and final assistant message for one accepted proxy response, even when calls overlap or a turn takes several attempts.

**Why this priority**: Scoring the wrong answer corrupts the comparison without an obvious error.

**Independent Test**: Run two overlapping synthetic turns in one session, with distinct expected message pairs, a retry, a tool follow-up and a control client. Use the same served model across different route decisions and reverse response arrival order.

**Acceptance Scenarios**:

1. **Given** two admitted terminal responses, **when** both turns are durably saved, **then** each response binds only to its own persisted user and final assistant message UIDs.
2. **Given** a billed retry, tool-only response, interrupted stream or response discarded after a user correction, **when** a later response supplies the saved answer, **then** only the proven terminal response is attributable. No “last successful response” fallback is allowed.
3. **Given** another configured alias on the same proxy, **when** its request meets the same rules, **then** it can be attributed without changing the plugin; its alias does not imply a router tier.

### User Story 2 - Qualify without scoring (Priority: P1)

As a router operator, I can run a read-only qualification pass that accounts for the whole selected cohort and stops rather than guessing when evidence is incomplete.

**Why this priority**: A report built only from successful joins can hide systematic loss.

**Independent Test**: Feed a fixed cohort with known `COMPLEX`, `REASONING`, excluded, missing, conflicting and late rows into a read-only evaluator. Spy on judge and ledger interfaces and compare the input stores before and after.

**Acceptance Scenarios**:

1. **Given** a complete cohort, **when** qualification runs, **then** `COMPLEX` joins are reported from persisted router decisions, `REASONING` is reported separately, and known exclusions are counted by reason. No judge runs and no score is written.
2. **Given** an expected terminal response or a potentially eligible trusted spend row with missing, stale, malformed or non-unique evidence, **when** its evidence cannot be resolved within the allowed read window, **then** the run returns `EVAL STALL` (exit `2`), reports the reason without raw identifiers, and emits no successful qualification verdict.

### User Story 3 - Opt in without changing inference (Priority: P2)

As a kit operator, I can enable or disable attribution for a single profile without changing what the router or Hermes sends, selects or displays beyond the permitted metadata.

**Why this priority**: Losing measurement must not take down inference or leak correlation data.

**Independent Test**: Compare plugin-off, plugin-on and simulated plugin failure against an instrumented local proxy, upstream sink and redirect sink. Observe all network hops and the user-visible result.

**Acceptance Scenarios**:

1. **Given** an explicitly allowed origin, endpoint and alias, **when** the request is sent, **then** only the local proxy receives the plugin's attribution metadata. Upstream, redirected and non-allowlisted destinations receive none.
2. **Given** disabled attribution, unsupported capabilities or a plugin write failure, **when** Hermes runs a turn, **then** ordinary inference is unchanged and the affected turn cannot qualify.

### Edge Cases

| Condition | Required outcome |
| --- | --- |
| SDK retries reuse a logical request ID or attribution token | Require exact accepted-exchange evidence and positive classification of nonterminal siblings. If reuse could refer to more than one accepted exchange, do not bind. |
| A tool follow-up, subagent, classifier, MCP, replay or discarded response shares a route, session or tier | Exclude only on affirmative evidence of its role or disposition. An unresolved potentially eligible event stalls. |
| A transform changes the displayed answer, or Hermes replaces, merges or compacts away a row | Bind only if Hermes proves the accepted response produced the exact physical final assistant row and the exact associated user row still exists. A surviving summary, absorbed UID or text match is not a substitute. |
| An accepted response arrives before its SpendLog or transcript commit | Keep the join pending. Never treat provisional data or a stream's opening headers as completion; apply the bounded qualification rule. |
| A transport can forward an attribution header after a redirect, provider fallback or middleware rewrite | Do not tag on that transport unless the final dispatch and every forwarding path satisfy the boundary. Do not alter inference redirect, fallback or retry policy to make attribution work. |
| A duplicate delivery, replay or conflicting concurrent write is observed | Identical local observation is a no-op. Conflicting evidence invalidates the identity for qualification; it cannot overwrite or resurrect a valid binding. |

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The kit MUST ship a separate, disabled-by-default Hermes plugin under `integrations/hermes/`, following the manifest, registration and documentation pattern of the [proxy lifecycle guard](../../integrations/hermes/proxy-lifecycle-guard/README.md). Operators MUST be able to validate the package with `hermes plugins validate`, opt in per profile, and disable or remove it independently of the guard. The plugin MUST use supported interfaces only, without core patches, private client interception, monkeypatches, a new proxy callback or service, or upstream schema changes.
- **FR-002**: Admission MUST require the exact configured loopback proxy origin (scheme, host and port), endpoint path and effective requested alias, verified before any tagged send. The alias allowlist MUST support `smart-router` and explicitly named alternatives without wildcards. The plugin MUST not tag detached, background, subagent or auxiliary traffic. When final destination or call scope cannot be proven, it MUST send no attribution tag and leave ordinary inference to Hermes.
- **FR-003**: The only new request data MUST be a namespaced, versioned, randomly generated opaque attempt token in `x-litellm-spend-logs-metadata`. The plugin MUST preserve unrelated headers and metadata; it MUST not adopt, overwrite or trust a pre-existing attribution key, or merge ambiguous or malformed header data. When such a conflict prevents safe tagging, mark attribution unavailable and leave the original request unmodified. The plugin MUST neither set nor replace `x-litellm-call-id`. No trace/affinity identifiers, Hermes message/session IDs, content or credentials may be added as attribution metadata.
- **FR-004**: The plugin MUST demonstrate that its header and token terminate at the configured proxy, including on HTTP redirects, Hermes fallback and proxy provider dispatch. Client-header forwarding MUST be off for the qualified path and no alternate forwarding rule may carry the tag. Deployment or transport drift that invalidates these guarantees MUST disable tagging until requalified. Apart from the permitted metadata, it MUST preserve prompt and tool payloads, response behavior, routing/tier decision semantics, affinity, credentials and trace-ID behavior. Attribution MUST neither send another inference request nor replay one after post-send failure.
- **FR-005**: A binding MUST originate from the exact `x-litellm-call-id` observed on the accepted response and the plugin-issued token on that exchange. The evaluator MUST require an exact match of both to `metadata.litellm_call_id` and the namespaced value in `metadata.spend_logs_metadata` on one authoritative LiteLLM SpendLog row. It MUST verify trusted proxy and client provenance independently of caller-controlled headers/metadata, detect conflicting duplicate IDs and token reuse in the qualified scope, and reject ambiguous joins. A logical request ID may join Hermes events but does not prove wire uniqueness. A 2xx, a provider response ID, a configured alias, a served model, a timestamp or session affinity cannot substitute for either join key or independently prove acceptance.
- **FR-006**: The plugin MUST prove which response Hermes accepted to produce the terminal assistant message for a completed, interactive turn. Before publishing a ready binding, it MUST verify the actual user and final assistant `message_uid` rows, roles, and same physical session in the canonical transcript store, using exact identities carried by supported lifecycle evidence. At qualification the evaluator MUST recheck both rows and prove that the bound revisions are still current, using supported revision evidence or a demonstrated immutability guarantee for both rows. A same-UID replacement, mutation or unknown revision MUST stall; UID, role and session alone do not establish continuing lineage. No text match, row order, attempt counter or recent-session lookup may establish identity. A transform is eligible only if the accepted-response-to-persisted-row lineage survives; failed, intermediate, replayed, superseded, synthetic recovery, detached and unpersisted outputs cannot stand in for the final answer.
- **FR-007**: Attribution state MUST be versioned and private to the active profile, under an XDG state root in a kit namespace keyed by that profile. Persist only the binding fields below; do not persist message bodies, prompts, tool arguments, credentials, raw headers or wire logs. Writes MUST publish atomically, be idempotent for identical evidence, and fail closed on conflicts, partial writes or unknown schema versions. Reader access MUST be exact and read-only; binding expiry MUST be enforced on read even if cleanup is delayed. V1 bindings and conflict markers expire at most 24 hours after observation and MUST be pruned automatically, including on the next start after downtime. Revision evidence MUST be non-content and expire with its binding. Expiry MUST be anchored to the original observation, not the newest delivery. If that original observation or active generation cannot be proved after pruning, a repeated event MUST NOT recreate the binding. This bound does not change native SpendLog or transcript retention.
- **FR-008**: The evaluator MUST fix the synthetic cohort scope and scheduled roster before dispatch by trusted proxy instance, authenticated client identity, route, transport, profile and generation. Each roster entry MUST link by exact trusted identity to its own Hermes outcome and, if eligible, its binding; matching counts are insufficient. Independently reconcile every in-scope proxy exchange and any separately logged billable attempts against the SpendLogs expected by the qualified runtime contract. Prove both event-to-log completeness and complete reads; an unexplained missing row stalls even when the terminal join succeeds. Neither side may be filtered by token or binding presence. First classify nonterminal or unrelated events using affirmative evidence and router tiers using trusted persisted `metadata.routing_decision.tier`. Proven nonterminal/unrelated events and recognized non-target tiers other than `REASONING` have a counted exclusion and do not need terminal bindings. Excluding a roster member by tier still requires independent exact linkage to the authoritative SpendLog for that outcome; an unlinked row cannot exclude a turn. A potentially eligible event with missing provenance, disposition or tier stalls. Then require a one-to-one join in both directions between eligible Hermes terminal outcomes and matching SpendLogs through their bindings. `COMPLEX` is the target tier and `REASONING` is qualified and reported separately. Non-router aliases qualify separately without a synthetic tier. The visibility retry may discover late rows within the original scope, but MUST NOT change the scope or roster.
- **FR-009**: Qualification MUST be read-only. A pass or `no samples` asserts an as-of verdict at one validated point before publication, based on a coherent view of roster outcomes, proxy records, binding conflicts, both transcript revisions, expiry and active generation. A change that invalidates the evidence before that point or prevents proving coherence MUST stall. The validated point, not the end of report delivery, determines the result. A later revocation invalidates reuse of the verdict; the verdict itself conveys no activation authority. Report qualified, positively excluded and unresolved terminal-roster members against the expected terminal count. A Smart Router pass requires at least one qualified `COMPLEX` sample; a complete `REASONING`-only cohort reports `no samples` for `COMPLEX` and retains its separate `REASONING` results. Account separately for excluded and unmatched proxy rows, with stable sanitized reason codes and separate tier totals; do not count retry rows as additional turns. Return `no samples`, never a pass, only when a complete read shows zero eligible samples for the requested cohort or tier and zero unresolved items. Retry only a positively identified transient visibility miss, once within an absolute 30-second budget from the first read. Other unresolved evidence or an incomplete read at the deadline MUST return `EVAL STALL` (exit `2`). Ambiguity, schema errors, missing provenance, expired bindings or unsupported versions MUST NOT be retried as lag. Time may bound reads and expiry, never assign identity.
- **FR-010**: Tagging and qualification MUST have separate controls; neither enables scoring. This feature MUST NOT expose a scoring control, even after a clean qualification pass. No judge calls, ledger writes, historic backfill, score mutation, scheduler changes or production enablement are in scope. Each exchange MUST retain the generation in which it was tagged. Disabling the plugin MUST stop new tags and revoke that generation for new ready bindings and verdicts, without interrupting ordinary inference or the tier census. In-flight events MUST NOT be reassigned to a later generation. A documented rollback MUST cover in-flight responses, local records still awaiting expiry, and tags already persisted in SpendLogs under the proxy's existing policy. Any later scoring activation requires a separately reviewed, versioned cohort and explicit operator approval.
- **FR-011**: Support MUST be recorded by exact Hermes build, LiteLLM build, endpoint, stream mode and relevant client/proxy configuration. For each advertised combination, prove the actual dispatch, response-header capture, terminal acceptance and durable identity chain through public interfaces, plus absence of tag egress. A disposable, explicitly authorized probe may exercise a candidate mode before qualification; this does not make that mode available for ordinary traffic. Outside that isolated probe, any unproven or changed combination remains untagged and unqualified. If a required path has no supported seam, record the precise gap with evidence and return it for spec review; do not silently narrow the two-endpoint acceptance bar.
- **FR-012**: Package docs MUST explain install, validation, opt-in, compatibility, qualification, diagnostics, retention and disable/rollback. Automated fixtures MUST exercise the positive and negative cases above without live secrets or services. Live canaries require separate operator authorization for the exact disposable profile, runtime/configuration, destination and request/spend limits. Receipts MUST name the observations and build/configuration under test, but contain only sanitized results, counts and synthetic labels, never raw production IDs, tokens, headers, transcripts, paths or credentials.

### Key Entities

| Entity | Owner and authority |
| --- | --- |
| **Admitted exchange** | The verified destination and client context, the opaque token the plugin issued, and the call ID observed on the accepted wire response. An HTTP or Hermes logical attempt is not necessarily the accepted exchange. |
| **Spend row** | LiteLLM owns the persisted call ID, token copy, trusted client/route evidence and router decision. A body model or alias alone cannot establish either provenance or tier. |
| **Persisted turn** | Hermes owns the physical session and exact user/assistant UIDs, row roles, and evidence connecting the accepted terminal response to those rows. The plugin does not modify the transcript. |
| **Local binding** | The plugin owns the schema version, cohort/generation reference, token, call ID, physical session ID, user and assistant UIDs, observation/expiry, non-content row revision evidence when needed, and disposition/reason. A record with incomplete identifiers is never ready. Conflicts remain non-ready and take precedence over an identical observation. |
| **Qualification cohort** | The evaluator owns read-side membership, exclusions and verdict. A cohort freezes its scope and population before checking joins. For V1, a controller-owned roster of bounded synthetic turns, fixed before dispatch and reconciled to Hermes terminal outcomes, supplies the independent population. It cannot be derived from binding writes. If any scheduled turn lacks a terminal outcome or a positively proven nonterminal disposition, the cohort is incomplete. Free-form profile traffic is out of scope for V1 qualification. |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: The concurrent fixture yields exactly the two expected message pairs, zero cross-turn or cross-client bindings and zero bindings to rejected attempts. A fixture with equal counts but mismatched roster and outcome identities MUST stall. An explicitly allowlisted alternate alias attributes its own response, with no manufactured tier.
- **SC-002**: Every missing, conflicting, expired, replay-ambiguous or unsupported case in the qualification fixture returns `EVAL STALL` with exit `2` when potentially eligible, and makes zero judge calls and zero ledger writes. A proven excluded row without a binding is counted by reason, but an unclassified row stalls. A dropped required SpendLog for a billed retry stalls even if the terminal join succeeds. A same-UID row mutation, conflict between reads or disable before the validation point cannot produce a pass. A transient missing row that becomes visible by the one permitted retry joins exactly once; a late row outside the budget does not turn the prior stall into a pass.
- **SC-003**: At least one authorized synthetic `COMPLEX` canary on each required endpoint yields exactly one eligible SpendLog row and the exact persisted input/output pair. For each advertised stream mode, the same evidence is required on that mode. Captures at local ingress, provider ingress and redirect/control destinations show zero attribution tag egress and no semantic differences beyond permitted metadata, using a deterministic control for routing, affinity and trace behavior.
- **SC-004**: In disabled and faulted cases, ordinary inference and the tier census still work, with zero new admissible qualification bindings. A disable/re-enable cycle does not admit the prior generation. Read-only qualification leaves prior ledgers unchanged and reports `REASONING` separately from `COMPLEX`.

## Assumptions

- V1 covers a single local proxy per qualification cohort and one opted-in profile per cohort. The 24-hour retention and 30-second qualification budget are conservative draft defaults, not measured runtime characteristics. If the budget cannot be met on the supported setup, revise it in review rather than silently widening it.
- Hermes v0.23.3 and LiteLLM v1.110.0 are source-inspection baselines, not supported runtime claims. A release or derived build is only supported at its exact qualified configuration. No plugin, live config, production proxy or evaluator is changed by this specification.
- The configured proxy and canonical transcript store are trusted local authorities. A compromised proxy, local account or plugin host is outside this guarantee. Unrelated clients on the same proxy are not trusted. If the proxy cannot distinguish the opted-in client using authenticated server-side evidence, there is no qualification.

## Source evidence and gates

- **Request and accepted response**: At Hermes v0.23.3, `agent/turn_api_request.py` passes turn/request IDs and destination context to `llm_request` middleware. `agent/turn_api_call.py` wraps the transport with `llm_execution`, but Hermes can still discard its returned response. `agent/turn_response_intake.py` reports a normalized `post_api_request` payload; it does not expose a public raw-header contract. `agent/served_model.py` captures different headers through an internal client hook, which is not a plugin interface. These findings are source inspection, not proof of supported capture. See [Hermes middleware](https://hermes-agent.nousresearch.com/docs/developer-guide/middleware) and [observer hooks](https://hermes-agent.nousresearch.com/docs/developer-guide/observer-hooks).
- **Persistence**: Hermes publishes turn context through `post_llm_call` in `agent/turn_finalizer.py`, and the local transcript schema exposes `message_uid`, role and session. Neither alone shows that both exact IDs are durable and attributable at hook time, especially for transformed, merged, compacted or interrupted turns. See [Hermes v0.23.3 source](https://github.com/NousResearch/hermes-agent/tree/v0.23.3).
- **Proxy**: [LiteLLM v1.110.0 source](https://github.com/BerriAI/litellm/tree/v1.110.0) parses the spend metadata header, builds the reply call ID and includes these values in spend metadata. It may accept a client-supplied call ID, so a returned ID by itself is not an authenticated identity. Effective metadata projection, tier and auth-field persistence, retry behavior, and provider non-egress still need proof on the exact build/configuration.

### Required transport matrix

| Intended path | Modes to investigate | State |
| --- | --- | --- |
| `/v1/chat/completions` | Non-streaming and streaming | Pending accepted-response and durable-message proof |
| `/v1/responses` | Non-streaming and streaming | Pending accepted-response and durable-message proof |

Both endpoints are required for V1. Investigate all four combinations before implementation; qualify at least one mode on each endpoint and advertise only modes with their own proof. A mode that cannot be proved remains disabled and must be documented as such. One endpoint, stream mode or raw test-client success cannot stand in for another or for a real Hermes turn. Other protocols are out of scope for V1.

### Before implementation or activation

1. **Public-interface feasibility** (kit maintainer): identify the supported per-mode seam for the accepted response header and the exact durable user/final-assistant UIDs and row-revision proof, and demonstrate the timeline with disposable synthetic turns. Show whether client and proxy retries can share identifiers and whether redirect/fallback forwarding is controllable without changing inference. If not, stop and review the missing seam.
2. **Cohort feasibility** (kit maintainer and evaluator owner): demonstrate independent cohort intake and authenticated client/route provenance using deployed fields, including missing tags, nonterminal work, and delayed or duplicate rows. Pin the trusted roster-to-outcome identity, event-to-log and read completeness signals, coherent verdict boundary and read limits before implementation. If supported seams cannot supply any of these, stop for spec review. Record limits as unverified until measured.
3. **Qualification** (operator authorization required for live canaries): after offline fixtures, run synthetic turns through the installed plugin and both endpoints, with scoring disabled. Keep only sanitized evidence of local send, accepted response, SpendLog projection, transcript readback, negative egress controls, and read-only evaluator verdict. Support status may change only for the tested combinations. Scoring remains a separate, always-gated decision because it can spend money and mutate evaluation records.
