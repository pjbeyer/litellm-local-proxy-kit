# Project tooling

This existing repository adopts the **generic** operating baseline from
[template v0.1.4](https://github.com/pjbeyer/phil-ai-project-template/tree/82dc6eae0730f888bb66a00e061242fb5b7e59fd).
The [Copier answers](../.copier-answers.yml) record provenance; do not run a
blanket Copier update over the kit. Its tests, runtime layout, and Beads
instance already exist and are not replaced by the template.

## Work in a fresh checkout

- **Development:** Git, `uv`, Python, and Make. Follow the README's offline
  checks. GitHub Actions use full commit pins and test on macOS and Ubuntu.
- **Tracking:** use `bd` with the existing `.beads/` configuration and hooks.
  Do not reinitialize the database or run shared-service or backup enrollment
  from a contributor worktree. Treat kit Beads records and attribution notes
  as public; do not add private records or raw prompts.
- **Specifications:** the checked-in `.specify/` contains the Hermes-first
  shell scaffold generated by [Spec Kit v1.0.7](https://github.com/github/spec-kit/tree/fe1d00e3ccaf495880aaf90fb0e17679e82f065b),
  its bundled first-party `agent-context` extension, and the kit constitution.
  In this worktree, use the pinned CLI without requiring a global install:

  ```sh
  uvx --from 'git+https://github.com/github/spec-kit.git@fe1d00e3ccaf495880aaf90fb0e17679e82f065b' specify integration status --json
  ```

  Read [the feature index](../specs/README.md) before implementation. The base
  scaffold does not install community extensions or recreate approval state.
- **Agent guidance:** [AGENTS.md](../AGENTS.md) defines the kit-specific rules;
  the [operating-baseline skill](../.agents/skills/project-operating-baseline/SKILL.md)
  carries the generic conventions.

## Install Hermes commands separately

The checkout contains project files, not installed Hermes commands. Spec Kit
v1.0.7 writes directly to `~/.hermes/skills/` and can overwrite existing skills;
its uninstall can remove unrelated `speckit-*` skills. Do not run either against
your normal home just to work on this kit. To prepare commands for review, render
in an empty temporary home and project:

```sh
stage=$(mktemp -d)
mkdir -p "$stage/home" "$stage/project"
(
  export HOME="$stage/home" HERMES_HOME="$stage/home/.hermes"
  cd "$stage/project" || exit 1
  cli='git+https://github.com/github/spec-kit.git@fe1d00e3ccaf495880aaf90fb0e17679e82f065b'
  uvx --from "$cli" specify init --here --integration hermes --script sh --non-interactive &&
    uvx --from "$cli" specify extension add agent-context
)
```

The output is `$stage/home/.hermes/skills/`. If the target Hermes profile
already has these commands, keep its reviewed copies. Otherwise, the profile
owner can review the generated skills and install the needed directories in that
profile's skill root. Never overwrite an existing skill as part of repo setup.
The CLI status check above only verifies project files. The presence of the
base `/speckit-implement` command does not clear a feature's validation gate.

## Release setup

Release Please manages `CHANGELOG.md`, `VERSION`, and its manifest. The
`0.1.0` entries are a baseline, not a published tag. The bootstrap commit
bounds the initial commit scan to reviewed history. Do not add deployment
pins or owner approval files to `extra-files`.

The workflow is inert until the owner sets the repository variable
`ENABLE_RELEASE_PLEASE` to `true` and authorizes the release workflow's GitHub
permissions. Then a qualifying conventional commit on `main` (or a dispatch
on `main`) can open or update a release PR. A release requires review and merge
of that PR. Check CI on the release PR before merging; PRs opened by the default
Actions token do not trigger ordinary pull-request workflows. Verify the tag
and GitHub release independently. See [publication checks](publication-readiness.md).
